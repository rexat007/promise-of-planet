## 2. الهدف

تصميم مسار مقيد وموثوق لاستقبال الملفات الثنائية للصور والمستندات المؤيدة للحقوق، مع عزل الملف قبل اعتماده، والتحقق الخادمي من البايتات ومصدرها، وإثبات العلاقة بسجل البيانات والحقوق الموجود. **هذا ليس تفويضًا للتنفيذ بعد.**

## 3. أسئلة بوابة المصدر — قراءة فقط

1. ما إعداد Firebase Storage الحالي الفعلي (`storage.rules`، إعدادات bucket، Functions، `package.json`، التبعية `firebase-admin/storage` أو البديل)؟ وهل ثمة خدمة رفع أو عمليات signed URLs موجودة؟ سجل رموز الملفات والأسطر.
2. ما مسار الصورة الأصلي/المشتقات في العقد المعتمد؟ هل تؤكد بايتات المصدر بالـSHA-256، وصيغة الملف من الـmagic bytes وفك الترميز الفعلي، وحدود حجم/أبعاد/بكسلات، ومنع الملفات المتعددة والترويسات المضللة؟ ما المكتبات الفعلية المتاحة دون تثبيت؟
3. هل يوجد نطاق quarantine خاص وسجلات حالة الاستقبال، ومن يستطيع القراءة/الكتابة؟ ما قواعد Storage الفعلية؛ لا تفترض أن وجود مسار يعني صلاحية رفع.
4. كيف تمنع ربط `assetId` أو `createdByUid` بصورة غير مملوكة للفاعل؟ كيف يُتحقق من هوية المُرسل، ownership، التكرار، إعادة الإرسال، وسباق إنشاء الكائن والسجل؟
5. كيف سيتم التعامل مع مستندات إثبات الحقوق بشكل منفصل عن صور التحرير: هوية الملف، أصل الـSHA، حالة التسجيل، المراجعة البشرية، سرية المستند، منعه من القراءة العامة، وربطه بأدلة IMG-F3-04؟ لا تعتبر `artifactSha256` الحالي برهانًا على ملف مفحوص.
6. ما حدود الاختبار المتاحة محليًا بلا اتصال أو مفاتيح إنتاج: الاختبارات الوحدوية والمحاكاة، والمحاكي الرسمي إن كان متاحًا فقط، والفجوات التي تحتاج بيئة تشغيل منفصلة؟
7. اقترح وحدة تنفيذ **متوسطة ومتماسكة** وقائمة سماح دقيقة، مع قرار STOP إذا تطلبت تثبيت تبعيات أو تعريض الملف العام أو تغيير عقد مقبول. افصل بوضوح ما يحتاج قرار المالك.

## 4. مخرجات بوابة المصدر

- جدول المصدر (ملف، رمز، أسطر، ما يثبته)، الوضع **EXISTS / ABSENT / UNCERTAIN** لكل مكون.
- نموذج تسلسل حياة مقترح `quarantine → byte verification → private durable storage → metadata registration → human rights review → later delivery gate`، باعتباره **مقترحًا** وليس حالة حالية.
- مقارنة بديل مسار الرفع الآمن (server mediated مقابل client upload with scoped authorization)، والمخاطر والتبعيات.
- الاختبارات المطلوبة ونتائج بوابة `READY_FOR_BOUNDED_IMPLEMENTATION` أو `BLOCKED_REQUIRES_DECISION`.
- لا كتابة ولا تغيير ملفات ولا Git/Push/Deploy.

## 5. سياسات ملزمة

- لا نشر آلي ولا إتاحة عامة للصور أو أدلة الحقوق بسبب وجود `Approved` وحدها.
- محاكاة الـSHA أو الثقة في MIME المرسل من المستخدم ممنوعة؛ الإثبات التقني يتطلب قراءة الملف الفعلي والتحقق منه.
- الصور والوثائق الخاصة لا تُعرض علنًا عبر Storage Rules أو signed URLs دون قرار تسليم مستقل.
- عدم تعديل أي وحدة سابقة مقبولة دون اكتشاف تعارض مثبت وتفويض منفصل.
- لا تعليمات جلب من GitHub باسم المسار، ولا افتراض قدرات Git داخل Studio.
- ممنوع تثبيت التبعيات/تنظيف مجلدات/`rm -rf`/بناء واسع أو نشر Firebase في Studio.
